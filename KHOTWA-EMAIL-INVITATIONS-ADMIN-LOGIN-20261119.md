# Khotwa — Deputy email activation and separate Main Admin login

This release was applied on top of **khotwa-main(3).zip**. Existing schools, students, parents, and operational features remain in place.

## URLs and permissions

| User | URL | Credentials / permission |
|---|---|---|
| Main Admin (مدير النظام) | `/admin-login` → `/admin` | Existing environment-defined `KHOTWA_ADMIN_EMAIL` and password; **no longer accepted on school `/login`** |
| School deputy (وكيل شؤون الطلاب) | `/login` | Email + self-chosen password, **only after activating the emailed link**; school-scoped data |
| Deputy activation | `/activate?token=...` | 48-hour, single-use link generated by system, no admin-generated password |
| Parents | `/parent-login` → `/parent` | Unchanged school code/phone/password login |

The Main Admin remains configured independently from school deputy accounts via `KHOTWA_ADMIN_EMAIL`, `KHOTWA_ADMIN_PASSWORD_HASH` and `KHOTWA_SESSION_SECRET`. Protect these secrets; do not put plaintext passwords in Coolify/GitHub. The admin may intentionally open a school's view via a signed switch-school action; deputies cannot access `/admin` or `/api/admin`.

## Configure outgoing invitation email in Coolify — Hostinger preferred

This update sends via your own **Hostinger Email SMTP mailbox** first. Resend is retained as an **optional fallback** if no Hostinger SMTP username/password is configured. Hostinger requires no Resend API key or webhook secret.

In Hostinger hPanel, go to **Emails → select your domain → Mailboxes** and create a dedicated mailbox (for example, `noreply@YOUR-MAIL-DOMAIN`). If your plan supports it, create a revocable app password from **Mailbox → Options → App passwords**, rather than using the normal mailbox password. SMTP credentials must never be committed to GitHub.

Set these values in **Coolify → Khotwa → Environment Variables**:

```env
KHOTWA_APP_URL=https://khotwa-ksa.com
KHOTWA_FROM_EMAIL=noreply@YOUR-MAIL-DOMAIN.com
KHOTWA_SMTP_HOST=smtp.hostinger.com
KHOTWA_SMTP_PORT=465
KHOTWA_SMTP_USER=noreply@YOUR-MAIL-DOMAIN.com
KHOTWA_SMTP_PASSWORD=YOUR-HOSTINGER-MAILBOX-OR-APP-PASSWORD
```

- `KHOTWA_APP_URL` must be the exact public HTTPS origin; it determines activation links.
- `KHOTWA_FROM_EMAIL` must be a **plain email address**, and it **must equal `KHOTWA_SMTP_USER`**. The application adds a branded From display name automatically.
- The SMTP connection uses implicit SSL/TLS on **port 465**. Port 587/STARTTLS is **not implemented** in this release. Check that your VPS allows outgoing TCP 465.
- `KHOTWA_SMTP_HOST=smtp.titan.email` is appropriate **only if your Hostinger email product is Titan Email**, not standard Hostinger Email. Verify under Hostinger → Emails → Connect Apps & Devices.
- Use the Coolify **secret/protected** setting for the mailbox/app password, and **Is Literal** if necessary to preserve passwords containing `$` characters through Docker Compose.
- `RESEND_API_KEY` and `RESEND_WEBHOOK_SECRET` are **not needed** for Hostinger. They may be removed or left unset; Hostinger SMTP has precedence when `KHOTWA_SMTP_USER` is present.

The modified `docker-compose.yml` passes the settings into the container and `scripts/launch-vps-preview.mjs` injects them into the Worker runtime environment. The SMTP sender uses the native Worker-compatible TLS socket API and does not add a second Docker service.

### Delivery status: know the difference

Hostinger's SMTP server returns acceptance after the message is submitted. **That is not proof the email was delivered, received, or read.** In إدارة المدارس the status is **«قبله خادم Hostinger للإرسال (لم يتأكد التسليم)»**, with delivery confirmation unavailable. The system still records password setup and first successful login automatically, which are stronger signals that the invitation was used.

For manual deliverability investigation, Hostinger's **Email Delivery Logs** show individual outgoing-message statuses: hPanel → Emails → select domain → **Email Logs** (the precise label can vary by plan). There is no Resend-style webhook for Hostinger SMTP configured in this release.

Optional Resend alternative (no Hostinger SMTP credentials): provide `RESEND_API_KEY`, a verified `KHOTWA_FROM_EMAIL`, and if needed `RESEND_WEBHOOK_SECRET` with the signed callback `/api/webhooks/resend`. This option is retained for backward compatibility, but is unnecessary when you use Hostinger.

## Deputy onboarding

1. Log in as Main Admin at `/admin-login`. Open **إدارة المدارس**.
2. Create/select a school. Under **وكلاء شؤون الطلاب** enter full name, real email, and assigned school.
3. Click **إنشاء الحساب وإرسال الدعوة**. The system stores an invalid pending password placeholder and an SHA-256 **hash** of a random activation token. The admin cannot view the password or the token.
4. The deputy receives a 48-hour activation link and creates their own password (minimum 12 characters). The link becomes unusable after successful activation.
5. The deputy logs in at `/login` with their email/password, only seeing their school's data.
6. The Main Admin sees four independent lifecycle checks:
   - SMTP accepted: Hostinger accepted the message for sending (does **not** prove delivery).
   - Delivery status: **unavailable automatically with Hostinger SMTP**. The optional Resend provider can still send signed delivery-status webhooks.
   - Password set: the activation form was successfully completed.
   - First successful login: the deputy authenticated to the school portal.

If the SMTP server rejects the request or is unconfigured, the account still appears with **فشل الإرسال**; click **إعادة إرسال الدعوة** once configuration is fixed. For existing deputies, **رابط تغيير كلمة المرور** sends a self-service password reset link. Their current password stays usable until they accept the new link. Consuming it immediately invalidates previous sessions and resets the first-login milestone. Stopping or moving a deputy invalidates prior sessions, as before.

Account invitation and account-activation status can be refreshed via **تحديث حالة الدعوات**. The system does not use email open tracking or claim the recipient personally read the message.

## Data migration, credit, and legal documents

- New migration: `drizzle/0022_deputy_email_activations.sql` adds invitation, activation and login-status fields; it retroactively marks **existing valid deputy password hashes** as activated so those accounts do not lose access.
- The migration does not delete any existing student, school, parent, or historical case rows. It clears the *one old fixed default deputy name* from the default `settings` row, if present. For other schools, deputy display names remain school-editable.
- The program's interface/footer/print design credit now reads **تطوير فريق نظام خطوة لإدارة المدارس**. Historical recorded event actors and the **original legal registration certificate** are not modified or falsified.

## Deployment and validation

1. **Back up** the persistent `/data/state` volume and note the currently deployed Git commit.
2. Replace the repository files with the complete updated archive, or copy every path from the changed-files archive. Keep the `scripts` folder intact; a missing test script will break the Docker build.
3. Add/verify the six Hostinger SMTP environment variables in Coolify. Preserve the existing admin hash exactly including the **literal `$` separators** (Coolify Is Literal / Docker Compose interpolation issue).
4. Redeploy. The startup launcher applies migration `0022` to the *existing* D1 data store.
5. Verify Main Admin logs in only at `/admin-login`, deputy logs in only at `/login`, and parents still use `/parent-login`.
6. Send a deputy invite to a controlled email, complete activation, check the first-login timestamp, and verify a deputy cannot access another school or `/api/admin`.
7. Verify your test email manually in the mailbox or Hostinger delivery logs; test re-invitation and disabled-account handling. Hostinger does not provide an automatic delivery webhook here.

**Runtime caveat:** The existing Dockerfile continues to run a local Wrangler/Miniflare **staging/preview** server. Although the security/unit tests pass, this is **not proof that the current runtime is hardened for production use with real student records**. Complete a production build, staging end-to-end testing, backups, and tenancy audit before widening access.
