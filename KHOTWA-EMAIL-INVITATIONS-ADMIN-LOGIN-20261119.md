# Khotwa — Deputy email activation and separate Main Admin login

This release was applied on top of **khotwa-main(3).zip**. Existing schools, students, parents, and operational features remain in place.

## URLs and permissions

| User | URL | Credentials / permission |
|---|---|---|
| Main Admin (مدير النظام) | `/admin-login` → `/admin` | Existing environment-defined `KHOTWA_ADMIN_EMAIL` and password; **no longer accepted on school `/login`** |
| School deputy (وكيل شؤون الطلاب) | `/login` | Email + self-chosen password, **only after activating the emailed link**; school-scoped data |
| Deputy activation | `/activate?token=...` | 48-hour, single-use link generated by system, no admin-generated password |
| Parents | `/parent-login` → `/parent` | Unchanged school code/phone/password login |

The Main Admin remains configured independently from school deputy accounts via `KHOTWA_ADMIN_EMAIL`, `KHOTWA_ADMIN_PASSWORD_HASH` and `KHOTWA_SESSION_SECRET`. Protect these secrets; do not put plaintext passwords in Coolify/GitHub. The admin may intentionally open a school's view via a signed switch-school action; deputies cannot access `/admin` or `/api/admin`.

## Configure outgoing email in Coolify

The release implements outgoing invitations with the **Resend HTTPS email API**, rather than using Hostinger's SMTP directly. Create a Resend account, verify a domain/subdomain under your control (DNS verification), and create an API key permitted to send from that domain.

Create these environment variables in Coolify (prefer secret/hidden values for keys):

```env
KHOTWA_APP_URL=https://khotwa-ksa.com
KHOTWA_FROM_EMAIL=Khotwa <noreply@YOUR-VERIFIED-DOMAIN.com>
RESEND_API_KEY=re_xxxxxxxxx
RESEND_WEBHOOK_SECRET=whsec_xxxxxxxxx
```

- `KHOTWA_APP_URL` must be the **actual public HTTPS origin**, with no path, so the emailed `/activate` link is correct.
- `KHOTWA_FROM_EMAIL` must use the verified sender domain (Resend permits a display name as shown). It is **not** the school deputy's email address.
- `RESEND_API_KEY` is used only server-side; the browser never receives it.
- `RESEND_WEBHOOK_SECRET` comes from the Resend webhook configuration, **not** the API key.

In the Resend dashboard create a webhook endpoint:

`https://khotwa-ksa.com/api/webhooks/resend`

Subscribe to `email.delivered`, `email.bounced`, `email.failed`, and `email.delivery_delayed`. Store the webhook's signing secret as `RESEND_WEBHOOK_SECRET` in Coolify, redeploy, then send a test invitation from `/admin`. The webhook requires signed Svix headers and checks that signatures are fresh. Do **not** paste the API key or webhook secret in a support chat or email.

The modified `docker-compose.yml` passes these variables into the container and `scripts/launch-vps-preview.mjs` copies them to the Worker configuration.

## Deputy onboarding

1. Log in as Main Admin at `/admin-login`. Open **إدارة المدارس**.
2. Create/select a school. Under **وكلاء شؤون الطلاب** enter full name, real email, and assigned school.
3. Click **إنشاء الحساب وإرسال الدعوة**. The system stores an invalid pending password placeholder and an SHA-256 **hash** of a random activation token. The admin cannot view the password or the token.
4. The deputy receives a 48-hour activation link and creates their own password (minimum 12 characters). The link becomes unusable after successful activation.
5. The deputy logs in at `/login` with their email/password, only seeing their school's data.
6. The Main Admin sees four independent lifecycle checks:
   - Provider accepted: the Resend API accepted the send request (does **not** prove delivery).
   - Delivered: Resend confirms delivery to the recipient mail server (does **not** prove the message was read).
   - Password set: the activation form was successfully completed.
   - First successful login: the deputy authenticated to the school portal.

If the email API fails or is unconfigured, the account still appears with **فشل الإرسال**; click **إعادة إرسال الدعوة** once configuration is fixed. For existing deputies, **رابط تغيير كلمة المرور** sends a self-service password reset link. Their current password stays usable until they accept the new link. Consuming it immediately invalidates previous sessions and resets the first-login milestone. Stopping or moving a deputy invalidates prior sessions, as before.

Account delivery status can be refreshed via **تحديث حالة الدعوات**. The system does not use email open tracking or claim the recipient personally read the message.

## Data migration, credit, and legal documents

- New migration: `drizzle/0022_deputy_email_activations.sql` adds invitation, activation and login-status fields; it retroactively marks **existing valid deputy password hashes** as activated so those accounts do not lose access.
- The migration does not delete any existing student, school, parent, or historical case rows. It clears the *one old fixed default deputy name* from the default `settings` row, if present. For other schools, deputy display names remain school-editable.
- The program's interface/footer/print design credit now reads **تطوير فريق نظام خطوة لإدارة المدارس**. Historical recorded event actors and the **original legal registration certificate** are not modified or falsified.

## Deployment and validation

1. **Back up** the persistent `/data/state` volume and note the currently deployed Git commit.
2. Replace the repository files with the complete updated archive, or copy every path from the changed-files archive. Keep the `scripts` folder intact; a missing test script will break the Docker build.
3. Add/verify the four email environment variables in Coolify. Preserve the existing admin hash exactly including the **literal `$` separators** (Coolify Is Literal / Docker Compose interpolation issue).
4. Redeploy. The startup launcher applies migration `0022` to the *existing* D1 data store.
5. Verify Main Admin logs in only at `/admin-login`, deputy logs in only at `/login`, and parents still use `/parent-login`.
6. Send a deputy invite to a controlled email, complete activation, check the first-login timestamp, and verify a deputy cannot access another school or `/api/admin`.
7. Verify the delivery webhook after email arrives and test re-invitation and disabled-account handling.

**Runtime caveat:** The existing Dockerfile continues to run a local Wrangler/Miniflare **staging/preview** server. Although the security/unit tests pass, this is **not proof that the current runtime is hardened for production use with real student records**. Complete a production build, staging end-to-end testing, backups, and tenancy audit before widening access.
