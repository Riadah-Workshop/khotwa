# Khotwa mobile apps (Android and iOS)

The apps are a thin native shell (`mobile/`, built with Capacitor) around the live website. Everyone signs in the same way as on the web, and every role sees the same screens. What the shell adds is what a website cannot do on its own:

| Feature | Who | What the shell does |
|---|---|---|
| Scan a product with the phone | Cafeteria agent / manager | The camera button opens the phone's own scanner (Google ML Kit on Android, the camera framework on iOS). It reads product barcodes only, and the code goes through the same check-digit validation as a typed one. If the scanner is missing the website's own camera reader takes over. |
| Arrival and leaving alerts | Cafeteria agent (his account shows nothing) | The position is followed while the app is closed, so arriving at and leaving the cafeteria is noticed without asking him. Only the two times are stored; the position is never stored or sent anywhere else. Android shows one standing system notification while this runs: the operating system requires it and the app cannot hide it. |
| Updates | Everyone | The website already shows an "update available / required" bar (Diagnostics > Releases sets the numbers). In the app the button starts the update: inside the app on Android from Google Play, the store page on iOS, or the download address you entered for a directly installed app. |
| Problem reports | Everyone | Crashes and failed requests are sent (without anything typed or seen) to the Diagnostics page that only the system administrator sees. The app also reports which phone permissions are on or off. |

Parents attach a transfer screenshot from the gallery and change a child's daily limit from the same screens in the app as on the web.

## What is in the repository

* `mobile/` : the shell. It holds the configuration and a few scripts, no hand-written native code. The `android/` and `ios/` projects are generated by `npm run add:android` / `add:ios` and are not committed.
* `.github/workflows/mobile.yml` : builds the shell on GitHub. Android produces an installable test app and checks that the built app holds every permission and the background-location service; iOS builds for the simulator, which proves it compiles. It runs only when `mobile/**` or the native bridge changes, on a `mobile-v*` tag, or by hand.
* `app/native/*` : the website's side. In a browser every function quietly does nothing or uses the browser's own version, so nothing here changes how the website works.

## First build (about 20 minutes, once)

1. In the GitHub repository set the **variable** `KHOTWA_APP_URL` (Settings, Secrets and variables, Actions, Variables) to the website's address, for example `https://school.example.com`. The app opens exactly this address, over https only.
2. Choose the application id **before the first store release**: it is permanent. The default is `com.riadah.khotwa`; set the repository variable `KHOTWA_APP_ID` (same place as `KHOTWA_APP_URL`) to change it.
3. Run the **Mobile apps** workflow (Actions tab, Run workflow). When it is green the Android app compiles.
4. Push a tag such as `mobile-v1.0.0` (it must equal the version in `mobile/package.json`) to publish an installable Android file (`khotwa-mobile-v1.0.0.apk`) on the repository's Releases page. This file is signed with a debug key: it installs on any phone that allows installing from outside the store, but Google Play will not take it.

The app version is `mobile/package.json` `version`. Raise it for every release; the Android version code and the iOS version number follow from it.

## Before the stores

These need accounts and keys only the owner can create, so they are not done here:

* **Google Play**: a Play developer account (one-time fee), an app signing key (keep the key file and its passwords safe, losing them means you can never update the app), and a release build signed with it. Play asks for a justification for "location all the time"; the text is: *the cafeteria agent's arrival and leaving at the cafeteria is recorded for the administrator; no position is stored*.
* **Apple**: an Apple Developer account, a distribution certificate and provisioning profile, and a Mac or the hosted build service to upload. Apple's review guideline 4.2 can reject apps that are only a website in a frame; the scanner, background arrival and in-app update are the native features that answer it, and the review notes should name them.
* **Push notifications** (administrator sees arrival the moment it happens even with the app closed): needs a Firebase project (Android) and an Apple push key (iOS). Until then the administrator receives the arrival and leaving alerts inside the app and website, and by e-mail where the cafeteria enabled it.
* **App icon and splash screen**: the generated project starts with Capacitor's default icon. Put a 1024 x 1024 `mobile/resources/icon.png` and a 2732 x 2732 `mobile/resources/splash.png` and run `npx @capacitor/assets generate`.

## Known limits (read before relying on it)

* **Not yet run on a phone.** Everything the website does with the shell is tested without a phone (`scripts/test-mobile-patch.mjs`); the build workflow proves the projects compile and carry the right permissions. How the scanner, the standing notification and background arrival behave on real phones, especially on makers that stop background apps aggressively, still has to be tried on at least one Android and one iPhone. Diagnostics will show a phone where the location permission is off.
* **Background-location plugin versions.** The community plugin for following the position in the background is not published for the newest Capacitor release in the same way as the official ones. `mobile/.npmrc` lets it install anyway; if the first build fails on it, the workflow log says so and the plugin can be swapped (`@capgo/background-geolocation`) without touching the website.
* **No lock file yet.** The first `npm install` resolves the newest compatible versions. After the first green run, commit `mobile/package-lock.json` so later builds use exactly the same versions.
* Battery-saver state and "location all the time" are not readable from the website; Diagnostics shows them as unknown until a later release of the shell reports them.
