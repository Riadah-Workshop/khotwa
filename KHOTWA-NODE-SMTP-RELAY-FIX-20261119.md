# Khotwa Hostinger SMTP — Native Node TLS relay fix (19 Nov 2026)

## Reason for this patch

A direct SMTP TLS test in the running Khotwa Docker container succeeded (`TLSv1.3`, valid certificate, `220 smtp.hostinger.com`), while Khotwa's Wrangler/Worker socket path reported `SMTP_STAGE_CONNECT`. The TLS connection problem is specific to the application runtime path, not basic Docker network access.

## Design

- Keep Khotwa's current Wrangler/Cloudflare Worker application, school tenancy, login and database unchanged.
- Add a private Node.js SMTP relay in the **same Docker container**, listening only at `127.0.0.1:3765` (not exposed by Docker or Coolify).
- Khotwa Worker calls the private relay via authenticated POST; the private relay submits mail to Hostinger using Node's native `node:tls`.
- The launcher generates a new random internal bearer token at startup and makes it available to Worker through its existing `dist/server/.dev.vars` file (mode 0600). No manually configured relay token is needed.
- The Worker sends only `to`, `subject`, `text` and `html` to the relay. SMTP login credentials remain in the Node process environment.
- SMTP acceptance means Hostinger accepted the message, **not** that the recipient read or received it.
- No database migration or student-data change is part of this patch.

## Modified and new files

1. `lib/hostinger-smtp.ts` — relay routing and safe errors; prior sender remains available for non-relay runtimes.
2. `lib/deputy-invites.ts` — pass relay configuration to mail sender and recognize safe relay failure codes.
3. `scripts/smtp-relay.mjs` — new loopback-only Node TLS SMTP sender.
4. `scripts/launch-vps-preview.mjs` — launch the private relay alongside Wrangler; provision an ephemeral internal token; check relay health and stop both processes together.
5. `Dockerfile` — include the Node relay in the runtime image and run the new test.
6. `scripts/test-node-smtp-relay.mjs` — private relay authentication and simulated SMTP protocol tests.

## Coolify settings

In Coolify → Khotwa → Environment Variables:

```env
KHOTWA_APP_URL=https://khotwa-ksa.com
KHOTWA_SMTP_HOST=smtp.hostinger.com
KHOTWA_SMTP_PORT=465
KHOTWA_SMTP_USER=noreply@khotwa-ksa.com
KHOTWA_FROM_EMAIL=noreply@khotwa-ksa.com
KHOTWA_SMTP_PASSWORD=<real mailbox or app password>
```

The SMTP username and sender must match. If `noreply@khotwa-ksa.com` is an alias rather than a real authenticated mailbox, switch both variables to a real mailbox, or create one with SMTP login access.

Do **not** configure `KHOTWA_SMTP_RELAY_URL` or `KHOTWA_SMTP_RELAY_TOKEN` manually. These are generated by the application launcher for the local relay. Do not publish port 3765 or add a proxy route to it.

## Deploy

1. Back up your Coolify persistent volume and database before code changes.
2. Upload the files to the **existing file paths at the GitHub repository root**. The complete ZIP contains one wrapping `khotwa-main` directory; do not accidentally commit an extra nested directory.
3. Verify all six changed/new files (listed above) are committed on the branch Coolify deploys.
4. Verify your SMTP environment variables are correct and secret values are not exposed in screenshots or GitHub.
5. Redeploy. Confirm Coolify Runtime Logs contain `Khotwa private SMTP relay listening on 127.0.0.1:3765` and the Khotwa preview startup line.
6. Open Main Admin → deputy list → **إعادة إرسال الدعوة** for a test account. Confirm status changes to `smtp_accepted`, then open the invitation and complete activation.
7. If the sender fails, capture the new safe error code and lines containing `khotwa_local_smtp_relay_failed` or `khotwa_deputy_invitation_failed` from runtime logs; redact credentials and activation tokens.

## Checks completed before packaging

Seven local tests passed: Khotwa authentication, origin policy, school tenancy, multi-school permissions, deputy invitations, existing SMTP protocol, and the new Node TLS relay. Tests use simulated SMTP responses and do not send actual emails. The **full production application build and real Hostinger email delivery have not been verified in Coolify**. In particular, local Worker-to-loopback HTTP connectivity must be verified on the running installation.

## Important operational note

This deployment still uses `wrangler dev --local` as an on-server staging runtime. That is not a hardened production deployment. Plan a production-ready runtime replacement separately; do not combine that migration with the email hotfix. Also make sure `https://khotwa-ksa.com` is served with a valid browser-trusted TLS certificate before deputies follow activation links.
