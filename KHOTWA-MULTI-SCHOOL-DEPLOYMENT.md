# Khotwa — Multi-school administration and parents portal (2026-11-19)

## What this release adds

- **Main administrator** (`/admin`): register schools, configure unique school codes, see student counts, create student-affairs deputies, assign/change their school, disable/re-enable accounts, reset their password, and enter a school using a signed session.
- **Student-affairs deputy** (`وكيل شؤون الطلاب`): email/password login via `/login`; all **local school-management records** (students, attendance, cases, reports, care, tasks, trips, evidence, settings, etc.) are scoped to the one school named in the deputy's authenticated session.
- **Built-in parents portal** (`/parent-login`, `/parent`): parents log in with **school code, mobile number, and temporary password**. They can read only the children specifically activated by the deputy at **بوابة ولي الأمر** in the existing dashboard. They can view attendance and non-sensitive case statuses; **no student editing or medical/family care details** are exposed. Parents can change their password.
- **Session revocation**: when a deputy/parent is disabled, moved, or has a password reset, existing cookies are rejected on subsequent requests. Identity and school headers are generated by the server, never trusted from browsers.
- Login attempt throttling using the shared D1 store.

## Compatibility and data isolation

This is a schema-compatible extension of the supplied archive. The original school's records are **not moved, modified, or wiped**; they stay in the existing tables (school ID `default`). Newly created schools receive isolated **physical** school-specific copies of the 23 operational tables, including their foreign keys and indexes. Each SQL query from the Khotwa application is rewritten to the correct table set based on a verified server-side session context. External visitor/message integrations use a legacy shared service. For security they remain available to the original school and are **blocked for additional schools** until a separate per-school external integration is implemented. They are not silently shared across schools.

Important: this is a code change requiring security and integration testing on **staging** before allowing real students/parents to access it. The existing Coolify runtime uses local Wrangler/Miniflare, which is labelled staging in the original Dockerfile. Do **not** treat it as a hardened multi-tenant production service without moving to a supported production runtime and completing live browser, authentication, database, recovery, and load tests.

## Recommended Coolify deployment sequence

1. Take a backup/snapshot of your existing `/data/state` persistent volume **before** changing the application. Also keep a copy of the old Git revision for rollback.
2. Replace project files with the release archive (or merge the changed files), commit and push to GitHub. The `docker-compose.yml` and existing environment variables are retained. The original `KHOTWA_ADMIN_EMAIL`, `KHOTWA_ADMIN_PASSWORD_HASH`, and `KHOTWA_SESSION_SECRET` continue to be the **Main Admin** credentials. Do **not** set a new database volume.
3. Deploy. The existing `scripts/launch-vps-preview.mjs` automatically applies pending SQL migrations from `drizzle/`, including **`0021_khotwa_multischool.sql`**, before starting the web worker. Check the logs for migration success. `/readyz` checks both original and new schema readiness.
4. Sign in through `/login` with the existing main administrator credentials, then open **`/admin`** (also linked from the dashboard header).
5. The existing school appears as **المدرسة الحالية** with code `MAIN`; you can rename it and change its code to your actual school. Check its student count against existing records before proceeding.
6. Create a second school (e.g., code `SCHOOL-002`). Create a deputy using their name, email, and school assignment. The one-time temporary password is shown only on creation/reset: deliver it securely.
7. Sign out; log in as that deputy and confirm that the new school contains **zero students**. Add a test student and verify the Main Admin can see its count, while the original school remains unchanged.
8. In the deputy's school, open **بوابة ولي الأمر**, enter a guardian mobile number that matches a registered active student, select the student(s), activate, and privately share the generated credentials, school code, and `/parent-login` URL. Parents can change passwords inside `/parent`.
9. Validate with **two schools and two parents** that deputies never see each other's students, and that each parent sees only the children explicitly authorized in their own school. Test disabling each account and verify its previous session stops working.

**Roll back with the old Git revision without deleting the persistent volume.** The new migration and school tables can remain in the database; they do not replace the original school tables. Do not delete a school directly from SQLite or reuse its code for another school without an explicit data migration.

## Next production-hardening items

- Move off the existing local Wrangler/Miniflare preview runtime before publishing to multiple schools.
- Audit tenant isolation with real HTTP/e2e tests over every Khotwa API route, especially imports, backups, evidence attachments, and optional services.
- Plan schema upgrades that also migrate **all existing school-specific table sets** whenever a new operational table or column is introduced; new schools clone the current base schema when created, but already-created schools will need schema synchronization for future code releases.
- Consider role audit logs, parent invitation delivery, periodic D1/R2 backups, password policy and password-change-on-first-login, and school-specific external visitor/message service configuration.
- Move to a dedicated supported production database strategy (e.g., normalized `school_id` columns and row-level policies, or truly separate databases per tenant) if usage grows substantially.
